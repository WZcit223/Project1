# Validation Specification — v0.1

Status: **Approved at Gate 0 (2026-09-27), v0.1 baseline** · 中文: [zh/validation.md](zh/validation.md)

> v0.1 validates the **framework**, not the real-world accuracy of synthetic data.
> Allowed claim: *"The framework validates synthetic data generation and scenario execution at the prototype level."*

## 1. Validation levels

| Level | Question | In v0.1? |
|---|---|---|
| **1 Engineering** | Do modules, APIs, plugins and the pipeline work? | ✅ |
| **2 Synthetic data (structural)** | Schema, types, constraints, ranges, relationships, reproducibility, provenance correct? | ✅ |
| **3 Scenario** | Do scenarios behave as specified and do strategies produce different outcomes? | ✅ |
| **4 Real-world algorithm / data** | Does synthetic data represent reality; do results hold on real operations? | ❌ Future — never claimed |

Maturity labels used in docs and UI: Demo · Prototype · Synthetic Validation · Real Data Validation ·
Production Validation. v0.1 reaches **Prototype + Synthetic Validation** only.

## 2. Level 1 — Engineering checks

| Check | Test location |
|---|---|
| Package imports, config loads, `/health` works | unit, integration |
| Registries: register, lookup by id/version, duplicates rejected | unit |
| Each plugin passes its contract tests | unit |
| Architecture rules R1–R3 ([architecture.md §2](architecture.md#2-dependency-rules-enforced)) | unit (import-graph test) |
| API → application → engines → result, end-to-end | integration |
| Golden Path | scenario |

## 3. Level 2 — Synthetic data checks

| Check | Criterion |
|---|---|
| Schema conformance | All fields present, correct dtypes, no unexpected nulls |
| Constraints | 100% of declared constraints pass (`ValidationReport.passed`) |
| Ranges | e.g. quantities ≥ 0 and integral, lead_time_std ≤ lead_time_mean, probabilities in [0, 1] |
| Relationships | All foreign keys resolve |
| Reproducibility | Same inputs + seed → identical `content_hash`; different seed → different hash |
| Provenance completeness | Record contains inputs, generator id/version, parameters, scenario, seed, transformations, output hash |
| Calibration sanity (descriptive only) | Report mean, variance, zero-share, weekly profile of synthetic vs reference; **not** a pass/fail equivalence claim |

## 4. Level 3 — Scenario checks (same seed, synthetic demand)

| Check | Criterion |
|---|---|
| High Demand | Total demand / baseline total demand ∈ [1.25, 1.35] |
| Demand Shock | Mean demand inside window / baseline inside window ≈ shock_multiplier (±10%); outside window ≈ baseline (±5%) |
| Supply Disruption | Mean realised lead time of POs placed in window ≥ baseline + 5 days; received qty in window ≤ ordered qty |
| Simulation responds | Stockout-day rate under High Demand or Supply Disruption ≥ baseline for the static strategy `reorder_point` |
| Strategies differ | At least two strategies differ in fill rate or total cost by a non-trivial margin under baseline |
| Accounting identity | For every item-day: opening = previous closing + arrivals; fulfilled + lost = demand; closing ≥ 0 |
| Metric correctness | Metrics recomputed from the ledger in the test equal reported metrics |

Thresholds are initial proposals; if tuning is needed it is recorded in the development log with reasons.

## 5. Test data policy

- Tests use `tests/fixtures/m5_like/`: a small, **synthetic**, M5-shaped fixture (e.g. 1 store,
  1 category, 10 items, ~3 years) generated by `scripts/make_m5_fixture.py` with a fixed seed and
  labelled `source_type=fixture`. No real M5 data is committed.
- Optional local check against the real M5 subset: `uv run pytest -m m5_local` (skipped when
  `data/raw/m5_subset/` is absent).

## 6. Validation report

Phase 14 produces `docs/validation-report.md` with the results of all Level 1–3 checks, the exact
commit, seeds and configuration, and an explicit "not validated" section (Level 4).
