# Validation Specification — v0.1

Status: **Approved at Gate 0 (2026-09-27); categories restated in Phase 14 (2026-09-28)** · 中文: [zh/validation.md](zh/validation.md)

> v0.1 validates the **framework**, not the real-world accuracy of synthetic data.
> Allowed claim: *"The framework validates synthetic data generation and scenario execution at the prototype level."*

## 1. Validation categories

v0.1 keeps four categories strictly apart. Each result is reported under exactly one of them
(`docs/validation-report.md`, generated by `scripts/validation_report.py`).

| Category | Question | Evidence in v0.1 | Status |
|---|---|---|---|
| **V1 Software / framework correctness** | Do modules, plugins and interfaces behave as specified? | Unit and contract tests; architecture import rules; synthetic-data structure (schema, constraints, relationships, reproducibility, provenance); metric definitions; failure modes (§2–3) | ✅ |
| **V2 Framework integration / Golden Path** | Does the whole pipeline work end to end, through every client interface? | Golden Path via workflow runner, HTTP Application API and browser UI; persisted datasets and provenance; reproducibility; no look-ahead (§2) | ✅ |
| **V3 Scenario & reference-data validation** | Do scenarios behave as specified, and does the framework run correctly on real reference data? | Scenario behaviour checks on the fixture (§4); checks on the committed M5 subset: canonical/hybrid data validation, descriptive calibration comparison, forecast backtest, Golden Path smoke run (§4.1) | ✅ prototype level; reference comparisons are **descriptive** |
| **V4 Real operational validation** | Do synthetic operations and results hold for a real warehouse? | None — needs real operational data and a pilot | ❌ Future — never claimed |

**The M5 dataset is not warehouse operational data.** M5 is store-level retail **sales** (Walmart; the
committed subset: store CA_1, department FOODS_3, top 50 items) with calendar and prices. In this
framework it is the **reference demand/sales environment**: synthetic demand is calibrated on it and
forecasts are backtested on it. Everything operational — warehouses, suppliers, lead times, costs,
initial inventory, purchase orders — is **synthetic** (the Hybrid Validation Environment). M5 records
**observed sales**, not demand, and has no inventory / on-hand information: zero observed sales may
reflect true zero demand, stockouts or other forms of demand censoring, and the reference data does
not allow these causes to be distinguished. **Zero observed sales ≠ confirmed stockout.** M5 is
therefore a proxy for demand, not true demand.

Earlier drafts used levels 1–4 (Engineering, Synthetic data structural, Scenario, Real-world): Level 1
and 2 map to V1 (engineering checks that exercise the whole pipeline are reported under V2), Level 3 to
V3 and Level 4 to V4.

Maturity labels used in docs and UI: Demo · Prototype · Synthetic Validation · Real Data Validation ·
Production Validation. v0.1 reaches **Prototype + Synthetic Validation** only.

## 3. V1 — Synthetic data structure checks

| Check | Criterion |
|---|---|
| Schema conformance | All fields present, correct dtypes, no unexpected nulls |
| Constraints | 100% of declared constraints pass (`ValidationReport.passed`) |
| Ranges | e.g. quantities ≥ 0 and integral, lead_time_std ≤ lead_time_mean, probabilities in [0, 1] |
| Relationships | All foreign keys resolve |
| Reproducibility | Same inputs + seed → identical `content_hash`; different seed → different hash |
| Provenance completeness | Record contains inputs, generator id/version, parameters, scenario, seed, transformations, output hash |
| Calibration sanity (descriptive only, reported under V3) | Report mean, variance, zero-share, weekly profile of synthetic vs reference; **not** a pass/fail equivalence claim |

## 4. V3 — Scenario checks (same seed, synthetic demand)

| Check | Criterion |
|---|---|
| High Demand | Total **expected** demand (noise_scale = 0) / baseline ∈ [1.25, 1.35]; sampled total demand clearly higher (> 1.15). On a short horizon the stronger seasonality also shifts the window mean (fixture: expected 1.345, sampled 1.24 because of Poisson noise on small counts) |
| Demand Shock | Mean demand inside window / baseline inside window ≈ shock_multiplier (±10%); outside window ≈ baseline (±5%) |
| Supply Disruption | Mean realised lead time of POs placed in window ≥ baseline + 5 days; received qty in window ≤ ordered qty |
| Simulation responds | Stockout-day rate under High Demand or Supply Disruption ≥ baseline for the static strategy `reorder_point` |
| Strategies differ | At least two strategies differ in fill rate or total cost by a non-trivial margin under baseline |
| Accounting identity | For every item-day: opening = previous closing + arrivals; fulfilled + lost = demand; closing ≥ 0 |
| Metric correctness | Metrics recomputed from the ledger in the test equal reported metrics |
| No look-ahead | Changing demand after a decision date D leaves forecasts from origins ≤ D, ledger rows and orders through D unchanged (integration test) |
| Fair comparison | Strategies compared via `engine.compare` see identical demand, supply draws and seed |

**Gate 8 acceptance (owner, 2026-09-27).** The framework can execute and fairly compare multiple
interchangeable replenishment strategies under identical controlled simulation conditions, with
reproducible results and explicit temporal information boundaries. This is **not** a claim that any
strategy (e.g. `dynamic`) is economically or operationally superior in the real world.

**Real-subset runs are descriptive / smoke-test evidence.** Strategy results on the committed M5 subset
(CA_1 / FOODS_3 / top 50, 91-day synthetic horizon, synthetic operations, one seed) show that the
pipeline runs on real reference demand; they are not evidence of economic or algorithmic superiority
and are never reported as validation results.

Thresholds are initial proposals; if tuning is needed it is recorded in the development log with reasons.

### 4.1 V3 — Reference-data checks (committed M5 subset)

| Check | Criterion |
|---|---|
| Canonical data | The M5 adapter's retail bundle passes all schema, constraint and key checks (pass/fail) |
| Hybrid environment | Reference tables + synthetic operations pass all checks, foreign keys resolve (pass/fail) |
| Calibration comparison | Mean, variation, zero share, weekday profile and item-level correlation of synthetic vs. reference — **descriptive**, no threshold |
| Forecast backtest | Rolling-origin WAPE / MAE / bias of the three forecast plugins on reference sales — descriptive; the test only asserts the plugins run and LightGBM beats the moving average |
| Golden Path smoke run | 4 scenarios × 3 strategies on the reference subset complete and reproduce — results are **descriptive**, never evidence of real-world superiority |

## 5. Test data policy

- V1 / V2 tests use `tests/fixtures/m5_like/`: a small, **synthetic**, M5-shaped fixture (1 store,
  ~10 items, ~3 years) generated by `scripts/make_m5_fixture.py` with a fixed seed and labelled
  `source_type=fixture`.
- V3 reference-data tests (`-m m5_local`) use the real M5 subset committed in `data/reference/m5_subset/`
  (owner-approved exception, CLAUDE.md §13; Kaggle rules apply). They also run in CI and are skipped
  only if the folder is absent.

## 6. Validation report

[`validation-report.md`](validation-report.md) is generated by `uv run python scripts/validation_report.py`:
it runs the V1, V2 and V3 test selections (pytest, JUnit counts per module), computes the V3
reference-data results, and records the commit, versions and seed. It ends with an explicit
"not validated" section (V4). Regenerate it for every release; do not edit it by hand.
